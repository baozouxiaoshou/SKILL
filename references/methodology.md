# 方法论参考（Methodology Reference）

> 通用方法论 + C/B 端差异对照

---

## 0. 场景判断（第一步）

接收到需求后，先判断场景类型。

### 判断三问
1. **用户是谁？** 个人消费者 / 专业人士
2. **核心痛点？** 体验情感 / 效率合规
3. **监管约束？** 无 / 有专门约束

### 场景判断表

| 线索 | C 端 | B 端轻量 |
|------|------|---------|
| 用户类型 | 个人消费者 | 员工 / 专业人士 |
| 痛点关键词 | 体验、情感、便捷 | 效率、合规、准确 |
| 业务关键词 | 用户增长、留存、活跃 | 流程、合规、协作 |
| 监管约束 | 通常无 | 通常有 |
| 决策周期 | 短 | 中长 |
| 周期迭代 | 周级 | 月级 |

## 1. INVEST 原则（通用）

| 字母 | 原则 | 检查问题 |
|------|------|---------|
| **I** | Independent 独立 | 故事间无强依赖 |
| **N** | Negotiable 可协商 | 细节可讨论 |
| **V** | Valuable 有价值 | 用户能感知到的价值 |
| **E** | Estimable 可估算 | 团队能评估大小 |
| **S** | Small 足够小 | 1 个 Sprint 内能完成 |
| **T** | Testable 可测试 | 有明确验收标准 |

## 2. KANO 模型（通用）

### 四象限/五型
- **基本型 M**：必须有
- **期望型 O**：越多越好
- **兴奋型 A**：有惊喜
- **无差异型 I**：有无都无所谓
- **反向型 R**：有了反而不满

### C/B 端 KANO 差异

| KANO | C 端解读 | B 端解读 |
|------|---------|---------|
| **M 基本型** | 没这个功能用户极差 | 没这个功能业务无法运转 |
| **O 期望型** | 体验加分项 | 效率提升项 |
| **A 兴奋型** | 差异化亮点 | 业务突破 / 行业领先 |
| **I 无差异** | 真的无差异 | 真的无差异 |
| **R 反向** | 慎重评估 | 坚决不做（合规风险）|

### B 端 KANO 补充
- **基本型（M）的下限更高**：合规功能永远优先
- **反向型（R）的容忍度更低**：B 端出错的代价远大于 C 端

## 3. MoSCoW 优先级（通用）

| 优先级 | 说明 | 比例建议 |
|--------|------|---------|
| **M**ust | 必须有 | ~60% |
| **S**hould | 应该有 | ~20% |
| **C**ould | 可以有 | ~20% |
| **W**on't | 这次不做 | - |

### B 端 MoSCoW 补充
- **Must 的边界更严**：合规、安全、审计永远 Must
- **Won't 的考量更长**：B 端变更成本高，需考虑未来扩展

## 4. JTBD（Jobs To Be Done）

核心思想：**用户不是在买产品，而是在"雇佣"产品完成任务**。

### C 端 JTBD 案例
```
当【我早晨起来不知道做什么运动时】
我想【跟着视频做一次 5 分钟的晨练】
以便【精神饱满地开始一天】
```

### B 端 JTBD 案例
```
当【我作为合规专员需要提交双语异常报告时】
我想【录入一次中文，自动生成中英双语版】
以便【不需要重复录入，且格式满足监管要求】
```

## 5. Persona 构造方法

### C 端 Persona
- **基础属性**：年龄/职业/收入/地域
- **行为模式**：典型一天/消费习惯/社交特征
- **心理特征**：痛点/目标/价值观

### B 端 Persona
- **角色身份**：职位/职级/部门
- **工作环境**：使用系统/工作内容/协作对象
- **业务指标**：核心 KPI/质量指标/合规指标
- **协作关系**：上下游/汇报线

## 6. Journey Map 5 阶段

### C 端旅程
```
认知 Awareness → 考虑 Consideration → 使用 Use → 留存 Retention → 传播 Advocacy
```

### B 端旅程
```
接收任务 Task → 准备 Prepare → 执行 Execute → 校对 Review → 提交 Submit → 归档 Archive
```

## 7. Story Splitting 拆分模式（通用）

8 种拆分模式：工作流/角色/数据/业务规则/接口/异常路径/操作类型/界面

详见前一版文档。

### B 端拆分补充
- **按角色拆分**：合规专员 / 主管 / 监管方各自独立故事
- **按合规维度拆分**：必填项 / 校验项 / 审计项独立
- **按版本管理拆分**：v1 生成 / v2 修改 / 版本对比独立

## 8. Definition of Done（DoD 完成定义）

### C 端 DoD
- [ ] 代码完成且提交
- [ ] 通过代码审查
- [ ] 单元测试覆盖率 > 80%
- [ ] 集成测试通过
- [ ] UI 还原设计稿
- [ ] 验收标准（AC）全部通过
- [ ] 埋点上线并验证
- [ ] 文档更新

### B 端 DoD（在 C 端基础上增加）
- [ ] **合规审查通过**
- [ ] **术语库已更新**
- [ ] **版本快照已生成**
- [ ] **审计日志已记录**
- [ ] **数据脱敏规则已应用**
- [ ] **多语言对照已生成**
- [ ] **跨部门审批已通过**
- [ ] **监管格式要求已验证**

## 9. 需求获取技术（通用）

| 技术 | 适用场景 |
|------|---------|
| 用户访谈 | 深度需求、共情场景 |
| 问卷调研 | 量化、批量验证 |
| 现场观察 | 真实场景、痛点挖掘 |
| Focus Group | 多方观点碰撞 |
| Workshop | 跨部门共识达成 |
| A/B 测试 | 决策验证（C 端为主）|
| 数据分析 | 行为模式识别 |
| 竞品分析 | 市场对标 |

### B 端补充获取技术
- **流程走查**：跟着专业人士跑一遍真实流程
- **合规对标**：参考同行业 / 同地区的合规产品
- **监管沟通**：与监管方对接口径
- **历史事件分析**：分析过往合规事件的根因

## 10. 反模式警示

### 通用反模式

| 反模式 | 错误示例 | 正确做法 |
|--------|---------|---------|
| 功能描述代替故事 | "我想要支付按钮" | "我想要一键完成支付" |
| 技术价值代替用户价值 | "以便系统记录" | "以便我下次能快速找到" |
| 故事过大 | "我想要完整社交系统" | 按子功能拆分 |
| 验收不可测试 | "界面美观" | 量化、可观察 |
| 角色泛化 | "作为用户" | 指定 Persona |
| 漏掉边缘场景 | 只考虑主流程 | 异常/空/边界 |

### C 端特有反模式
- 忽略用户情感
- 漏掉留存/增长指标
- 文案缺乏同理心

### B 端特有反模式
- 忽略合规维度
- 漏掉版本快照
- 权限设计过于简单
- 术语不统一
- 漏掉审计追溯
- 协作流程不清晰

## 11. 场景选择决策树

```
接收到需求
  ↓
[Step 0] 是否是 C 端？
  ├─ 是 → 用 C 端方法论（体验优先、增长指标）
  └─ 否 → 是否是 B 端轻量？
            ├─ 是 → 用 B 端方法论（合规优先、效率指标）
            └─ 否 → 是否需要专用技能？
                     ├─ 复杂业务建模 → 推荐 BABOK Skill
                     ├─ 跨系统集成 → 推荐架构师 Skill
                     └─ 不明确 → 询问需求方
```
