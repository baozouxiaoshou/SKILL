# 需求评审检查清单（Story Review Checklist）

> 通用检查项 + C/B 端专项检查

---

## 一、用户故事质量（INVEST）

### I - Independent（独立）
- [ ] 故事间无强依赖，可独立开发
- [ ] 可以调换开发顺序而不影响整体
- [ ] 没有"必须先做 X 才能做 Y"的强约束

### N - Negotiable（可协商）
- [ ] 细节可讨论，不是死板的合同
- [ ] 留有与开发/设计协商的余地
- [ ] 没有过度细节（写到代码层面的）

### V - Valuable（有价值）
- [ ] 用户能感知到的价值（不是技术价值）
- [ ] 不是"系统记录"、"数据上报"这类技术语言
- [ ] 价值能映射到业务指标

### E - Estimable（可估算）
- [ ] 团队能评估大小（故事点）
- [ ] 没有"未知技术"导致无法估算
- [ ] 不大到无法拆分

### S - Small（足够小）
- [ ] 1 个 Sprint 内能完成
- [ ] 不超过 8 个故事点
- [ ] 没有"完整 XX 系统"这种范围

### T - Testable（可测试）
- [ ] 有明确的验收标准（AC）
- [ ] AC 可以无歧义测试
- [ ] QA 能据此写测试用例

---

## 二、验收标准质量

### 完整性
- [ ] 主流程 AC
- [ ] 边界场景 AC（输入边界、状态边界）
- [ ] 异常 AC（网络异常、业务异常）
- [ ] 权限 AC（未登录/无权限）
- [ ] 性能 AC（响应时间、加载时间）
- [ ] 兼容性 AC（设备/系统版本）
- [ ] 数据 AC（持久化、加密）

### B 端必含（在通用基础上增加）
- [ ] **合规性 AC**：是否符合行业法规 / 内部规范
- [ ] **安全性 AC**：数据加密、访问控制、权限边界
- [ ] **可追溯 AC**：版本快照、审计日志
- [ ] **可审计 AC**：监管复核、跨部门审计
- [ ] **协作 AC**：多人协作、审批流
- [ ] **术语 AC**：专业术语库覆盖
- [ ] **脱敏 AC**：敏感数据处理（如有）
- [ ] **多语言 AC**：双语/多语言对照（如需要）

### 可测试性
- [ ] 没有"界面美观"、"性能良好"这种模糊词
- [ ] 没有"应该正常工作"
- [ ] 用了 Given-When-Then 三段式

### 颗粒度
- [ ] 一个 Story 3-7 个 AC
- [ ] 每个 AC 聚焦一个点

---

## 三、用户视角检查

### Persona 具体性
- [ ] 故事中"作为 XX"指定了具体 Persona
- [ ] Persona 是真实的、可被团队记住的
- [ ] 不同故事可对应不同 Persona

### 用户价值清晰度
- [ ] "以便 XX" 是用户价值
- [ ] 用户能用自己的语言说出这个价值
- [ ] 不需要解释技术实现

### 场景化
- [ ] 故事发生在具体场景
- [ ] 不是脱离场景的功能列表
- [ ] 可对应到 Journey Map 的某阶段

### B 端额外检查
- [ ] Persona 的角色职责清晰
- [ ] 工作场景真实（不是凭空想象）
- [ ] 上下游协作关系明确
- [ ] KPI/合规要求准确

---

## 四、优先级合理性

### 通用
- [ ] 是否覆盖了基本型需求（Must）？
- [ ] 是否识别了兴奋型（亮点）？
- [ ] 是否排除了无差异型和反向型？

### 业务价值
- [ ] 是否与北极指标对齐？
- [ ] 是否有过程指标？
- [ ] 是否有反向指标（警惕的副作用）？

### 实现成本
- [ ] 工作量合理
- [ ] 没有遗漏依赖
- [ ] 风险识别到位

### B 端额外检查
- [ ] **合规底线是否优先识别**？
- [ ] **审计追溯是否作为 Must**？
- [ ] **权限边界是否在早期定义**？

---

## 五、技术可行性

### 可行性
- [ ] 当前技术栈能实现
- [ ] 没有未知风险
- [ ] 依赖团队/系统已就绪

### 依赖与阻塞
- [ ] 依赖的设计稿已就绪
- [ ] 依赖的接口已对齐
- [ ] 第三方服务已确认

### 边界与异常
- [ ] 异常处理方案明确
- [ ] 数据回滚方案明确
- [ ] 性能指标可达成

### B 端额外检查
- [ ] **跨部门协作流程已明确**？
- [ ] **监管对接已确认口径**？
- [ ] **数据脱敏规则已确定**？
- [ ] **版本快照存储已规划**？

---

## 六、文档完整性

### 必备内容
- [ ] 业务背景 / 价值说明
- [ ] 用户画像引用
- [ ] 用户旅程引用
- [ ] 优先级标注
- [ ] 故事点估算
- [ ] 验收标准
- [ ] 埋点方案
- [ ] 依赖与风险

### B 端额外
- [ ] **合规要求说明**
- [ ] **审计追溯设计**
- [ ] **术语库覆盖说明**
- [ ] **权限矩阵说明**
- [ ] **数据脱敏规则**

### 可视化
- [ ] 复杂流程配 Mermaid 图
- [ ] 状态流转有状态图
- [ ] 用户旅程有 Journey Map
- [ ] B 端：协作流程有泳道图

---

## 七、AB 实验设计（适用时）

### 假设
- [ ] 假设清晰、可证伪
- [ ] 因果链合理

### 设计
- [ ] 有对照组
- [ ] 样本量足够
- [ ] 实验周期覆盖完整业务周期
- [ ] 流量分配合理

### 决策规则
- [ ] 显著性判定规则
- [ ] 提前停止规则
- [ ] 回滚方案

---

## 八、场景适配检查

### 场景判断
- [ ] 明确识别场景类型（C 端 / B 端轻量 / 混合）
- [ ] 输出侧重与场景匹配
- [ ] 方法论用对（C 端看体验、B 端看合规）

### C 端额外
- [ ] 是否有增长实验空间？
- [ ] 是否有留存指标设计？
- [ ] 用户情感是否有考虑？

### B 端额外
- [ ] 是否有合规要求设计？
- [ ] 是否有审计追溯设计？
- [ ] 是否有版本快照机制？
- [ ] 是否有术语库设计？
- [ ] 是否有权限边界设计？

---

## 评分规则

| 维度 | 权重 | 得分 |
|------|------|------|
| INVEST 质量 | 20% | /100 |
| AC 质量 | 20% | /100 |
| 用户视角 | 15% | /100 |
| 优先级合理 | 15% | /100 |
| 技术可行 | 15% | /100 |
| 文档完整 | 10% | /100 |
| 场景适配 | 5% | /100 |
| **总分** | **100%** | **/100** |

**通过条件**：
- 总分 ≥ 60
- 且 INVEST + AC 两项 ≥ 40
- B 端场景：合规相关检查项 ≥ 70
