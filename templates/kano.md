# KANO 模型分类模板

> 通用方法 + C/B 端场景化应用

## KANO 模型基础

```
                    满意度
                      ↑
                  兴奋型 ●
                      │  ╱
                      │╱
        ──────────────●──────────→  实现度
                   ╱   │
                  ╱    │
              期望型    │
                  ╲    │
                   ╲   │
                   ● 无差异
                   │
                  基本型 ●
```

## KANO 四象限（实际五型）

| 类型 | 特性 | 策略 |
|------|------|------|
| **基本型 (M)** | 必须有，没了用户极度不满 | 必备底线 |
| **期望型 (O)** | 越多越好 | 持续打磨 |
| **兴奋型 (A)** | 没有不会不满，有了惊喜 | 差异化亮点 |
| **无差异型 (I)** | 有没有都一样 | 不做 |
| **反向型 (R)** | 有了反而引起不满 | 坚决不做 |

---

## C/B 端 KANO 差异

| 维度 | C 端 | B 端轻量 |
|------|------|---------|
| **基本型边界** | 没这个功能用户极差 | 没这个功能业务无法运转 |
| **期望型目标** | 体验加分项 | 效率提升项 |
| **兴奋型定位** | 差异化亮点 | 业务突破 / 行业领先 |
| **反向型容忍** | 慎重评估 | 坚决不做（合规风险） |
| **时间漂移** | 快（今天的兴奋→明天的期望） | 慢（B 端更稳定） |

## 评估流程

### Step 1：列出需求清单
```
需求 1：[功能 A]
需求 2：[功能 B]
需求 3：[功能 C]
```

### Step 2：对每个需求做 KANO 问卷（每条问两问）
- 正向问：[如果有这个功能]，你的感受是？
- 反向问：[如果没这个功能]，你的感受是？

### Step 3：套用 KANO 评估表

| | 不满意（反向） | | | | |
|---|---|---|---|---|---|
| **满意（正向）** | 喜欢 | 理所当然 | 无所谓 | 能忍受 | 不满意 |
| 喜欢 | Q | A | A | A | O |
| 理所当然 | R | I | I | I | M |
| 无所谓 | R | I | I | I | M |
| 能忍受 | R | I | I | I | M |
| 不满意 | R | R | R | R | Q |

### Step 4：汇总分类

## 优先级决策矩阵

### C 端场景
| KANO | 业务价值高 | 业务价值中 | 业务价值低 |
|------|----------|----------|----------|
| **M 基本型** | P0 立即做 | P0 立即做 | P1 必做 |
| **O 期望型** | P0 立即做 | P1 必做 | P2 可做 |
| **A 兴奋型** | P1 必做 | P2 可做 | P3 后做 |
| **I 无差异** | 不做 | 不做 | 不做 |
| **R 反向** | 不做 | 不做 | 不做 |

### B 端轻量场景
| KANO | 业务价值高 | 业务价值中 | 业务价值低 |
|------|----------|----------|----------|
| **M 基本型** | P0 必做 | P0 必做 | P1 必做 |
| **O 期望型** | P0 必做 | P1 必做 | P2 评估 |
| **A 兴奋型** | P1 必做 | P2 可做 | P3 后做 |
| **I 无差异** | 不做 | 不做 | 不做 |
| **R 反向** | **坚决不做** | 坚决不做 | 坚决不做 |

**B 端差异说明**：
- 基本型（M）永远 P0 必做
- 反向型（R）"业务价值低"时也要避免（合规风险）
- 期望型（O）的优先级上调（效率是 B 端关键）

## 注意事项

### C 端 KANO 特点
1. KANO 是**用户满意度**视角
2. 时间维度变化快：今天的 A → 明天的 O → 后天的 M
3. 不同用户群 KANO 不同：要分群评估

### B 端 KANO 特点
1. 基本型（M）的范围更广：合规、安全、审计都是 M
2. 反向型（R）的红线更多：合规风险、审计不通过
3. 时间维度变化慢：专业人士的期望更稳定
4. 用户群相对单一：但内部仍可能有不同角色（合规专员 vs 监管对接员）
